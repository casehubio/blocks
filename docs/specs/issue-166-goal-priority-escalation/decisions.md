# Decisions — #166/#160/#159 Goal Priority Escalation + Cross-Axis Composition

## D1: Escalation policy lives in blocks, not engine-api

**Choice:** `GoalEscalationPolicy` SPI and `NarrativeGoalEscalationPolicy` implementation both live in blocks. GoalProposalOrchestrator evaluates escalation before converting proposals to `GoalFormationProposal.ProposedGoal`, setting `suggestedPriority = PRIMARY` when warranted. DefaultGoalFormationService (engine) already respects `suggestedPriority()` — no engine-api SPI needed. GoalProposalOrchestrator acquires NarrativeState via an optional `Instance<NarrativeOrchestrator>` dependency (see D8). When NarrativeOrchestrator is absent or returns `Optional.empty()`, escalation evaluation is skipped — no narrative evidence, no escalation. Engine-side provenance enforcement is specified in D7.
**Alternatives:**
- Engine-api SPI with generic context (`Map<String, Object>`) — lossy typing, runtime casting, indirection without value. The engine would need to populate context it doesn't understand (NarrativeState, DriveProfile are blocks types).
- Engine-api SPI with eidos-api projections — pollutes the zero-dep foundation module with types it shouldn't own
- D11 (#142 spec) sketch: `GoalPriorityEscalationPolicy` in engine-api with `GoalEscalationContext(@Nullable NarrativeState, @Nullable DriveProfile)` — circular dependency: engine-api cannot depend on blocks
**Rationale:** All three inputs to the escalation decision (NarrativeState, DriveProfile, DriveGoalProposal) are blocks-owned. The output is GoalPriority (eidos-api), which blocks can already reference. Revocability (D11 governance contract) requires continuous re-evaluation on every GoalProposalOrchestrator tick — this is a compositor concern that can't live in the engine's one-shot registration path. Sustained alignment tracking requires NarrativeState.synthesisedAt() monitoring, which is blocks-local state. The D11 spec's placement was a design sketch that didn't account for the dependency graph — the intent (governed escalation) is correct, the placement was wrong.
**Trade-offs:** Engine has no built-in governance for PRIMARY escalation. Mitigated by defence-in-depth enforcement in DefaultGoalFormationService (see D7): rejects PRIMARY on drive-sourced goals without `escalatedBy` provenance. This guard is architecturally load-bearing — without it, the governance contract is voluntary compliance.
**Sources:** D11 (#142 decisions), D6 (#136 decisions), GoalFormationService.java (engine-api), DefaultGoalFormationService.java (engine runtime — line 103: uses suggestedPriority as-is), GoalProposalOrchestrator.java (blocks — evaluateRelevance pattern), DriveComposer.java (blocks — modulation algebra precedent)
**Exploration:** deep-analysis
**Status:** captured

## D2: Cross-axis composition as internal pipeline step with optional LLM enrichment

**Choice:** Cross-axis composition is a private pipeline step within GoalProposalOrchestrator, not a separate public SPI. Heuristic detection is inline: scan NarrativeState themes for DerivedThemes with ≥2 axes having **positive** axisModulationWeight > config threshold (sign-aware, consistent with D5's positive-only alignment and D6's positive-only dominant axis selection). A theme that suppresses one drive and amplifies another is a single-axis theme, not a cross-axis composition candidate. Compose compound DriveGoalProposals using the theme's dominant axis (see D6). Optional LLM enrichment via `Instance<CrossAxisGoalEnricher>` — when resolvable, enriches compound goal descriptions with narrative-aware context; when absent, heuristic descriptions ("explore-and-connect-{topic}") are used. GoalProposalOrchestrator pipeline: (1) per-axis mapping, (2) cross-axis composition, (3) escalation evaluation, (4) ranking + capacity.
**Alternatives:**
- Public `CrossAxisGoalComposer` SPI with heuristic + LLM implementations — creates CDI resolution ambiguity (`Instance<CrossAxisGoalComposer>` with two beans requires `@Alternative` or `@Qualifier`), adds indirection for a single consumer. The only consumer is GoalProposalOrchestrator.
- CrossAxisGoalMapper only (heuristic only) — locks out LLM composition
- LLM-only via DriveGoalFormationStrategy extension — every cross-axis evaluation costs an LLM call
**Rationale:** Follows the existing GoalProposalOrchestrator pattern: evaluateRelevance() and evaluateMappers() are already internal pipeline steps. The heuristic/LLM selection uses the same `Instance.isResolvable()` cascading pattern as DriveGoalFormationStrategy (optional CDI bean, check resolvability, fall back to inline logic). This is a two-type cascading pattern (inline heuristic + optional LLM enricher), not a single SPI with two implementations — DriveGoalFormationStrategy and DriveGoalMapper are two separate SPIs with different signatures, resolved independently by the orchestrator.
**Trade-offs:** Less "pluggable" than a public SPI — alternative composition strategies require modifying the orchestrator's private method. Acceptable given exactly one consumer and the established internal-step pattern.
**Depends on:** D1 (escalation policy placement — cross-axis proposals also go through escalation), D6 (axis semantics for cross-axis proposals), D8 (NarrativeOrchestrator dependency provides NarrativeState)
**Sources:** GoalProposalOrchestrator.java (blocks — evaluateRelevance/evaluateMappers pattern), DriveGoalFormationStrategy.java + DriveGoalMapper.java (blocks — two-type cascading fallback precedent), D11 (#142 decisions — cross-axis foundation types)
**Exploration:** quick → revised after decision review (R1-05, R1-06, R1-07, R2-02)
**Status:** revised

## D3: Sustained alignment via synthesis-cycle tracking with goal-attribute persistence

**Choice:** Escalation and demotion both use synthesis-cycle tracking. Governance state is persisted in goal attributes, surviving process restart through AgentRegistry persistence. The orchestrator never writes attributes directly — it emits governance state signals in `GoalProposalTick.Changes` (see D4), and the consumer/scheduler applies them via `AgentRegistry.register()`. This preserves the compositor's side-effect-free guarantee.

Escalation tracking: GoalProposalOrchestrator stores `escalation.firstAlignedSynthesisAt` and `escalation.alignedCycleCount` in an in-flight tracking map during tick evaluation. On each tick, if `NarrativeState.synthesisedAt()` differs from the last-checked timestamp, a new synthesis has occurred — verify alignment still holds (DerivedTheme.salience > threshold AND axisModulationWeight for proposal's axis > minAxisWeight, sign-aware per D5). If yes, increment cycle count. If no, reset to zero. When the count reaches `escalationCycles` (default: 2), the proposal is escalated to PRIMARY and the timestamps flow into `ProposedGoal.attributes` as `escalation.firstAlignedSynthesisAt` and `escalation.escalatedAt`.

Demotion tracking: for registered PRIMARY drive-sourced goals, the orchestrator reads existing `escalation.lastAlignedSynthesisAt` from goal attributes (passed in via AgentDescriptor). On each tick, if `NarrativeState.synthesisedAt()` has advanced beyond `lastAlignedSynthesisAt` and alignment no longer holds, increment a demotion counter. When the counter reaches `demotionCycles` (default: 2), emit a `PriorityAdjustment` demotion signal. Governance attribute updates (`escalation.lastAlignedSynthesisAt`, `escalation.misalignedCycleCount`) are emitted as `List<GovernanceAttributeUpdate>` in the `GoalProposalTick.Changes` variant — the scheduler applies them alongside proposals, abandonments, and priority adjustments. If alignment is re-confirmed, the update resets the counter and updates `lastAlignedSynthesisAt`.
**Alternatives:**
- In-memory-only tracking (original choice) — simpler, but demotion counters reset on restart, leaving stale PRIMARY goals indefinitely. Violates D11's revocability requirement.
- Time-based window (escalate after duration D) — counts idle periods where no synthesis occurred as "sustained alignment." Weaker evidence: time elapsed ≠ narrative re-evaluated.
- Per-tick counter (N consecutive ticks) — narrative only changes at synthesis boundaries, so many ticks between syntheses count the same alignment state repeatedly. Inflates the counter without new information.
- Dedicated persistence store — new SPI for governance state. Over-engineering when AgentGoal.attributes already provides a persisted key-value store co-located with the governed entity.
**Rationale:** D11's governance contract specifies "persist across multiple synthesis cycles." A synthesis cycle means the LLM re-evaluated the narrative and the theme survived — that's genuine confirmation of alignment. Synthesis is gated by the composite trigger (count + novelty + quiet period, per D6 in #142), so cycles are infrequent and meaningful. Symmetry between escalation and demotion (both use cycle counting) prevents thrashing. Goal attributes provide persistence without a new store — governance state is co-located with the governed entity and survives restart through AgentRegistry.
**Trade-offs:** Escalation is slow — minimum 2 synthesis cycles before PRIMARY. This is intentional (D11 governance contract: "ungoverned escalation is dangerous"). In pathological cases where synthesis never triggers (no new reflections, no quiet period bypass), escalation never happens — also intentional; no narrative evidence, no escalation. Governance attribute updates add a fourth signal type to `GoalProposalTick.Changes` (alongside proposals, abandonments, priority adjustments), increasing the consumer's application surface. This is the correct cost — the orchestrator must remain a pure compositor.
**Depends on:** D1 (escalation policy placement), D4 (Changes carries governance signals), D5 (sign-aware alignment check)
**Sources:** D11 (#142 decisions — governance contract: sustained alignment, revocability), NarrativeState.synthesisedAt() (blocks — synthesis timestamp), AgentGoal.attributes (eidos-api — persisted key-value store), NarrativeSynthesisGate (blocks — composite trigger gating synthesis frequency), GoalProposalOrchestratorTest.compositorGuarantee_noSideEffects (blocks — compositor purity test)
**Exploration:** quick → revised after decision review (R1-11, R1-12, R1-22, R2-03)
**Status:** revised

## D4: Priority adjustments bundled in GoalProposalTick.Changes (renamed from Proposed)

**Choice:** Rename `GoalProposalTick.Proposed` → `GoalProposalTick.Changes`. The record carries four co-occurring signals from a single tick evaluation: `List<DriveGoalProposal> newProposals`, `List<String> abandonedGoalNames`, `List<PriorityAdjustment> priorityAdjustments`, and `List<GovernanceAttributeUpdate> governanceUpdates`. `PriorityAdjustment` is a new record: `(String goalName, GoalPriority newPriority, String reason)`. `GovernanceAttributeUpdate` is a new record: `(String goalName, Map<String, String> attributeUpdates)` — carries demotion tracking state changes (escalation.lastAlignedSynthesisAt, escalation.misalignedCycleCount) that must be persisted in goal attributes. The scheduler reads all four signals and applies them atomically: register new proposals via GoalFormationService, remove abandoned goals, update priorities via `AgentGoal.toBuilder().priority(newPriority).build()`, update governance attributes via `AgentGoal.toBuilder().attributes(merged).build()`.
**Alternatives:**
- Separate sealed permits (`Proposed`, `Abandoned`, `Adjusted`) — cleaner per-signal semantics but these signals co-occur naturally from a single evaluation. Atomic application matters: the scheduler must see all changes together, not as independent messages. Splitting requires either multiple ticks (breaks the tick pattern) or a composite return (which is what Changes already is).
- Keep `Proposed` name — misleading: the variant already carries abandonments (not proposals) and would now carry adjustments and governance updates (not proposals). The name describes neither the primary nor the only use case.
**Rationale:** Priority adjustments and governance attribute updates co-occur with proposal evaluation — they're part of the same tick. A tick that proposes new goals AND demotes existing ones AND updates governance tracking state is normal (narrative changed → old alignment dropped, new alignment detected, demotion counter advanced). The rename from `Proposed` to `Changes` accurately describes the variant's purpose. Zero production callers exist (only test callers verified via call hierarchy), making this rename zero-cost. The signal-based approach preserves the compositor's side-effect-free guarantee: the orchestrator evaluates and returns signals; the consumer/scheduler applies them (including AgentRegistry writes for governance attributes).
**Trade-offs:** `Changes` carries four signal types, increasing the consumer's application surface. Acceptable — atomic application of co-occurring signals is the correct pattern; splitting signals across ticks or variants would lose the atomicity guarantee.
**Depends on:** D3 (synthesis-cycle tracking produces the escalation/demotion signals)
**Sources:** GoalProposalTick.java (blocks — existing sealed interface), GoalProposalOrchestrator.doTick() (blocks — constructs Proposed with both proposals and abandonments), GoalProposalOrchestrator.tick() call hierarchy (blocks — only test callers, no production consumers)
**Exploration:** quick → revised after decision review (R1-15, R1-16, R2-03)
**Status:** revised

## D5: GoalEscalationPolicy SPI shape and alignment definition

**Choice:** `GoalEscalationPolicy` is a `@FunctionalInterface` SPI: `@Nullable EscalationResult evaluate(DriveGoalProposal, GoalEscalationContext)`. Returns null for no escalation, `EscalationResult(GoalPriority, String themeLabel, String reason)` for escalation with provenance. `GoalEscalationContext` carries `NarrativeState`, `DriveProfile`, and `AgentDescriptor`. Alignment is defined as: DerivedTheme.salience > `escalationSalienceThreshold` (default 0.6) AND theme.axisModulationWeights.get(proposal.axis()) > `minAxisAlignmentWeight` (default 0.3) — sign-aware, positive weight only (negative weight = suppression, disqualifies escalation). `NarrativeGoalEscalationPolicy` implements this with an additional guard: no escalation if a PRIMARY drive-sourced goal already exists in the descriptor (cap at 1 PRIMARY escalation). Same-tick cap enforcement: the GoalProposalOrchestrator tracks in-flight escalations during tick evaluation; if multiple proposals qualify for PRIMARY in a single tick, only the highest-scoring (by driveIntensity) is kept at PRIMARY — the rest revert to SECONDARY. This coordination is at the orchestrator level, not in the policy SPI.
**Alternatives:**
- Return `GoalPriority` directly (no provenance) — loses the theme label and reason needed for goal attributes and audit trail
- Omit AgentDescriptor from context — policy can't check existing goal state, can't cap PRIMARY count
- Boolean return instead of EscalationResult — same as GoalPriority but less flexible for future priority tiers
**Rationale:** The @FunctionalInterface pattern matches DriveGoalMapper and DriveGoalFormationStrategy. Nullable return for "no change" matches DriveGoalMapper's pattern. EscalationResult carries provenance that flows directly into `GoalFormationProposal.ProposedGoal.attributes`: `{"escalatedBy": "narrative", "theme": themeLabel}`. The alignment definition is a conjunction of two signals: salience (how central the theme is to identity) and axis weight (how much the theme influences this specific drive). Both must be significant for escalation — a peripheral theme with a strong axis weight, or a central theme with weak axis relevance, don't justify PRIMARY.
**Trade-offs:** The salience and axis weight thresholds are configurable but the alignment definition (conjunction, sign-aware) is fixed in the SPI contract. A future policy that uses a different alignment metric (e.g., weighted product instead of conjunction) would need a new implementation, not reconfiguration. Acceptable — the alignment semantics are the policy's domain. Demotion and escalation of different goals cannot occur in the same tick: the pre-tick AgentDescriptor snapshot shows the demoting goal G1 as PRIMARY, so the cap check blocks new escalation of G2. After the scheduler applies the demotion, the next tick sees G1 as SECONDARY and can escalate G2. This one-tick delay is intentionally conservative — consistent with the "sustained alignment" governance philosophy.
**Depends on:** D1 (blocks-local SPI), D3 (synthesis-cycle tracking calls this policy)
**Sources:** DriveGoalMapper.java (blocks — @FunctionalInterface nullable return pattern), DerivedTheme.java (blocks — salience + axisModulationWeights, weights in [-1, 1] where negative = suppression), DriveComposer.java (blocks — narrative modulation: `intensity += narrativeModulation.getOrDefault(axis, 0.0) * config.narrativeModulationStrength()`, negative weight reduces intensity), GoalFormationProposal.ProposedGoal.attributes (engine-api — provenance attributes), D11 (#142 decisions — governance contract)
**Exploration:** quick → revised after decision review (R1-18, R1-20, R2-04)
**Status:** revised

## D6: Cross-axis proposal axis() semantics — primary axis

**Choice:** Cross-axis proposals use the source theme's dominant axis (highest positive axisModulationWeight) as `DriveGoalProposal.axis()`. The compound nature is captured in `goalDescription` (describes multi-axis goal), `formationReason` (explains cross-axis provenance), and flows through to `GoalFormationProposal.ProposedGoal.attributes` as `crossAxisWeights` (serialised map of all contributing axes and their weights from the source theme).
**Alternatives:**
- New `CrossAxisGoalProposal` record type — breaks D5's `GoalEscalationPolicy.evaluate(DriveGoalProposal, ...)` signature and all downstream consumers. A new type for a specialisation of the same concept adds complexity without functional benefit.
- `List<DriveAxis>` or `Set<DriveAxis>` replacing single `axis()` — changes every consumer of DriveGoalProposal. The single-axis case (which is the majority) now wraps a single element in a collection.
- Sentinel axis value (e.g., `DriveAxis.COMPOUND`) — breaks the enum's psychological grounding (SDT + intrinsic motivation). The four axes are not arbitrary; a fifth "compound" value has no psychological meaning.
**Rationale:** The `axis()` field serves two purposes: (1) escalation alignment checking — the policy checks the theme's weight for `proposal.axis()`, which is the dominant axis, giving a meaningful alignment signal; (2) tracking and deduplication — proposals are identified partly by axis, and the dominant axis provides a stable identifier. The full axis composition is preserved in attributes for any consumer that needs it. This follows the same pattern as multi-source events carrying a primary source with metadata for secondary sources.
**Trade-offs:** Lossy — a compound curiosity+affiliation proposal only shows CURIOSITY as its axis(). Downstream code that filters by axis would miss the affiliation component. Mitigated by `crossAxisWeights` in attributes for consumers that need the full picture.
**Depends on:** D2 (cross-axis composition pipeline step)
**Sources:** DriveGoalProposal.java (blocks — single axis record), DerivedTheme.axisModulationWeights (blocks — per-axis weights that define cross-axis significance)
**Exploration:** surfaced-by-review (R1-08, R1-19)
**Status:** captured

## D7: Engine-side provenance guard for PRIMARY drive-sourced goals

**Choice:** `DefaultGoalFormationService.propose()` adds a validation check: if a `ProposedGoal` has `suggestedPriority = PRIMARY` AND `attributes.get("source") = "drive"`, then `attributes.get("escalatedBy")` must be non-null. Reject with reason "drive-sourced PRIMARY requires escalation provenance" if the guard fails. This is a stateless, context-free check — the engine doesn't evaluate whether escalation is warranted (that's the policy's job in blocks), it enforces that the escalation went through the governance pathway.
**Alternatives:**
- No engine guard (original D1 trade-off characterisation) — any blocks component setting `suggestedPriority = PRIMARY` bypasses the governance model. The escalation policy is voluntary compliance.
- Engine-api SPI for escalation validation — over-engineering for a stateless attribute check. The guard is a simple conditional in one method, not a pluggable concern.
- `GoalFormationProposal.ProposedGoal` record validation — rejects at construction time. But construction happens in blocks, which already knows the rules. The guard's value is at the engine boundary.
**Rationale:** The D11 governance contract (sustained alignment, revocability) is meaningless if any producer can set `suggestedPriority = PRIMARY` without going through the escalation pathway. The engine can't evaluate whether escalation is warranted (lacks blocks context), but it CAN enforce that PRIMARY on drive-sourced goals carries provenance. This is defence-in-depth: the policy in blocks is the primary enforcement; the engine guard catches bypass.
**Trade-offs:** Engine runtime change required (DefaultGoalFormationService modification). The guard is additive — existing non-drive-sourced goals (case-assigned) can still be PRIMARY without provenance. Only drive-sourced goals require escalation provenance.
**Depends on:** D1 (policy in blocks produces the provenance that the guard checks)
**Sources:** DefaultGoalFormationService.java (engine runtime — line 103: `p.suggestedPriority() != null ? p.suggestedPriority() : GoalPriority.SECONDARY`), GoalFormationProposal.ProposedGoal.attributes (engine-api — provenance attributes), D11 (#142 decisions — governance contract)
**Exploration:** surfaced-by-review (R1-02)
**Status:** captured

## D8: NarrativeOrchestrator as optional GoalProposalOrchestrator dependency

**Choice:** GoalProposalOrchestrator gains an optional `Instance<NarrativeOrchestrator>` dependency, following the same pattern as `Instance<GoalSignalStore>`. When `narrativeOrchestrator.isResolvable()`, escalation evaluation is enabled: `currentNarrative(agentId, tenantId)` provides NarrativeState for the GoalEscalationContext. When absent or returning `Optional.empty()`, escalation is skipped entirely — drive-sourced goals remain SECONDARY.
**Alternatives:**
- Direct constructor injection (non-optional) — makes the narrative module a hard dependency. GoalProposalOrchestrator can't function without it, even for non-escalation use cases (basic drive-to-goal mapping).
- NarrativeState supplier function (`Function<String, Optional<NarrativeState>>`) — decouples from NarrativeOrchestrator type but loses CDI lifecycle management. Consumer must wire the function manually.
- No coupling — keep GoalProposalOrchestrator narrative-free, introduce a separate EscalationOrchestrator that wraps GoalProposalOrchestrator and adds escalation. Over-engineering for a concern that's intrinsically part of the goal proposal pipeline.
**Rationale:** Escalation is a pipeline step within goal proposal evaluation (per D1 and D2's pipeline). It reads NarrativeState the same way the orchestrator reads DriveProfile — as input to a pipeline stage. Optional `Instance<>` is the established pattern for dependencies that enrich but aren't required: `Instance<GoalSignalStore>` provides outcome-based abandonment when available, `Instance<DriveGoalFormationStrategy>` provides LLM-backed goal formation when available. NarrativeOrchestrator follows the same pattern.
**Trade-offs:** Couples two previously independent subsystems (drives/goals and narrative). This coupling is correct — narrative-informed escalation requires narrative. Testing: mock NarrativeOrchestrator in unit tests (same as mocking DriveOrchestrator). Initialization order: D10 from #142 defines NarrativeOrchestrator ticks before GoalProposalOrchestrator. Absent narrative module: safe default (no escalation, drive-sourced goals stay SECONDARY).
**Depends on:** D1 (escalation policy placement)
**Sources:** GoalProposalOrchestrator.java (blocks — Instance<GoalSignalStore> optional dependency pattern), NarrativeOrchestrator.currentNarrative() (blocks — returns Optional<NarrativeState>), D10 (#142 decisions — tick ordering)
**Exploration:** surfaced-by-review (R1-03, R1-23)
**Status:** captured
